# Real-Time Language Translator — Development and Troubleshooting Summary

## Overview

This document summarizes the development, architecture, debugging, testing, optimization discussions, and GPU setup attempts for the **Real-Time Language Translator** project.

The project is intended to be a browser-based, two-way language translation application. A user speaks into the microphone, the browser captures the audio, sends it to a Python backend through WebSockets, the backend transcribes the speech, translates the recognized text into another language, generates speech from the translation, and returns both the translated text and audio to the browser.

The primary objective is to create an efficiently working **real-time language translator** using technologies that are free and open source wherever possible.

The project is now being approached as a rebuild because the earlier implementation gradually became complex, accumulated multiple errors, and became difficult to debug.

9. Original Whisper Integration

The original implementation used the standard OpenAI Whisper Python package.

The model was loaded when the backend started:

    "tiny",

An important positive aspect of this approach is that the model is loaded only once.

The model should not be loaded for every request because that would significantly increase latency.

The intended behavior was:

10. Original ASR Utility

The function:

A significant problem was discovered: the transcription language was hardcoded.

This means the ASR system would always expect English regardless of the language selected by the user.

For multilingual translation, the source language should either:

Be dynamically passed to the ASR function, or
Be automatically detected by Whisper.

12. Important Configuration Naming Problem

A significant inconsistency existed between different versions of the frontend and backend.

One frontend version sent:

{
  "source_lang": "en",
  "target_lang": "hi",
  "tts_voice": "hi-IN-SwaraNeural"
}

Another backend version expected:

{
  "source_language": "en",
  "target_language": "hi",
  "voice": "hi-IN-SwaraNeural"
}

These names are not equivalent.

source_lang ≠ source_language
target_lang ≠ target_language
tts_voice ≠ voice

The rebuilt project should use one standardized protocol everywhere.

A recommended format is:

{
  "type": "config",
  "source_language": "en",
  "target_language": "hi",
  "tts_voice": "hi-IN-SwaraNeural"
}

The same names should be used in:

Frontend
Backend
WebSocket test files
Documentation

23. MediaRecorder and WebM

The original frontend used:

This generates audio chunks approximately every second.

The chunks were sent through the WebSocket.

24. Important WebM Audio Problem

A major issue was discovered with this design.

WebM is a container format.

Individual MediaRecorder chunks are not always independently valid WebM files.

Simply concatenating arbitrary WebM chunks can produce invalid audio.

This can cause errors such as:

Invalid data found when processing input

Therefore, real-time audio streaming must be designed carefully.

The backend pipeline should first be tested using a complete valid audio file.

Only after the complete pipeline works should continuous streaming be implemented.

27. Why the Dummy Audio Test Failed

The dummy audio consisted of arbitrary bytes.

For example:

b"\\x00" * 1024

These bytes are not valid WebM audio.

The backend attempted to process them as audio.

The ASR library failed with:

InvalidDataError:
Invalid data found when processing input

This means the test data itself was invalid.

A complete valid audio file is required for meaningful ASR testing.

28. sample.webm Testing

A sample.webm file was generated for testing.

A generated tone or sine wave can test whether the audio container is readable.

However, it cannot properly test speech recognition.

For a real ASR test, the file should contain actual human speech.

For example:

Hello, how are you today?

This allows the complete pipeline to be tested properly.

This indicated that a CUDA library required by the ASR runtime was unavailable.

33. GPU Diagnostic Results

A CUDA diagnostic script produced:

cuDNN enabled: True
cuDNN version: 90100
Device count: 1
Current device: 0

This is an important result.

It means:

PyTorch CUDA = working
GPU accessible to PyTorch = yes

Therefore, the GPU hardware itself was not the primary problem.

34. CUDA Version Mismatch

PyTorch reported:

CUDA 11.8

However, faster-whisper or its underlying runtime attempted to load:

cublas64_12.dll

This indicates a CUDA runtime mismatch.

Conceptually:

PyTorch environment
    ↓
CUDA 11.8

ASR runtime requirement
    ↓
CUDA 12 library

These environments were inconsistent.

This caused the GPU inference failure.

35. Environment Variable Problems

The diagnostic script reported:

CUDA_PATH: Not Set
PATH includes CUDA bin: False

It also checked:

C:\\Program Files\\NVIDIA GPU Computing Toolkit\\CUDA\\v12.1

and reported missing CUDA DLLs there.

This indicated that the development environment was not configured consistently.

36. libnvvp

The setup process also searched for:

libnvvp

The folder was not found.

This is not a critical problem for this project.

libnvvp is related to NVIDIA profiling tools and is not required for normal GPU inference with Whisper.

Its absence should not be treated as the primary problem.

37. Important Correction About GPU Cleanup

A previous idea was to remove GPU-related setup and confirm cleanup by checking whether:

torch.cuda.is_available()

became False.

That is not the correct definition of a clean environment.

The NVIDIA GPU driver should generally remain installed.

The correct cleanup approach is:

Keep the NVIDIA graphics driver.
Remove conflicting CUDA Toolkit installations if necessary.
Remove manually installed conflicting cuDNN files if applicable.
Remove incorrect CUDA environment variables.
Delete and recreate the Python virtual environment.
Install compatible dependencies from scratch.

The goal is not to make the GPU disappear.

The goal is to create a clean and compatible software environment.

43. Recommended Optimization Principles

The final application should prioritize low latency and reliability.

Load the ASR Model Once

Do not load Whisper for every request.

Load it when the backend starts.

Use GPU Acceleration When Correctly Configured

Use:

device = cuda
compute_type = float16

only after confirming that all required GPU libraries are compatible.

Use Smaller Models for Faster Response

Start with:

tiny or base

Then compare speed and transcription quality.

Maintain One Message Protocol

Frontend, backend, and test scripts should use identical JSON field names.

Test Components Independently

Do not debug:

GPU
WebSocket
ASR
Translation
TTS
Browser audio

all at the same time.
